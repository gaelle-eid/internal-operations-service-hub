# ADR-001: Request history and comments are append-only, on a relational store

## Status
Accepted

## Context
`product-spec.md` requires that request history and comments be preserved and auditable, with no silent edits or deletes. This matters because requests can involve HR or Finance matters where it may later be important to prove exactly what was said, by whom, and when — and because department staff and requesters need to trust that the record of a request hasn't been quietly altered after the fact.

We had two options for how to model this in `data-model.md` and enforce it in `architecture.md`:
1. Allow comments and status changes to be edited/deleted, and rely on convention (UI hiding the buttons, staff being trusted not to misuse admin access) to keep the record honest.
2. Make comments and status history append-only at the data and API level — no "edit" or "delete" operation exists for past entries, so there is nothing to misuse.

We also had to decide what kind of database to build this on: relational or document.

## Decision
We chose option 2: comments and status history entries are append-only. Once written, an entry can never be edited or deleted — corrections happen by adding a new entry (e.g., a new comment, or a new status transition), not by altering an old one. This is enforced by not exposing edit/delete operations for these entities in the API, not just by hiding them in the UI (see `architecture.md`, Trust + Resilience). In the data model, this is reflected by a separate `StatusHistory` entity rather than only storing the current status directly on `Request`.

For storage, we chose a **relational database, specifically PostgreSQL**, over a document database:
- Our entities have fixed, well-defined relationships (`Department` 1-N `Users`, `Department` 1-N `Requests`, `Request` 1-N `Comments`, `Request` 1-N `StatusHistory`) — exactly what relational databases enforce well via foreign keys.
- Department isolation ("HR staff can't see IT requests") is a hard rule. A foreign key plus a constraint enforces it at the database level, so it can't be silently violated by an application bug — a document database would leave that check entirely to application code.
- The append-only audit trail depends on referential integrity: every `Comment` and `StatusHistory` entry must reference a real `Request` and a real `User`, and relational foreign keys guarantee that; nothing should exist as an orphaned or mismatched record.
- Our most important queries are relationship-heavy (department queue by status, a request's full history) — natural SQL joins and filters, not the kind of self-contained nested documents that document databases are optimized for.
- Our schema is small and stable (5 entities, not expected to change shape rapidly), so we don't need a document database's flexibility for an unpredictable or deeply nested schema.
- PostgreSQL specifically: free and open-source (no licensing concerns for a student project), strong constraint/referential-integrity support (which matters given how much of the model leans on foreign keys for authorization and isolation), and it still supports JSON columns if we ever need some flexible/semi-structured data later — so we're not locked out of flexibility where it isn't the default.

## Consequences
- **Positive:** The audit trail is trustworthy by construction, not by convention — even an admin with elevated access cannot quietly rewrite what happened on a request. This directly satisfies the "no silent edits/deletes" requirement.
- **Positive:** Department isolation and history preservation reinforce each other — since department staff can only act within their own department's requests, and nothing they do to a request's history can be un-done, disputes about "who changed what" have a clear, permanent answer.
- **Positive:** Choosing PostgreSQL means our authorization and audit guarantees are backed by the database itself (constraints, foreign keys), not just application logic that could have bugs.
- **Trade-off:** Simple typo fixes in a comment aren't possible — a user has to post a follow-up comment instead of correcting the original. We accepted this trade-off because it's a minor inconvenience compared to the trust guarantee it buys.
- **Trade-off:** `Request.status` is a derived/denormalized field that must always agree with the latest `StatusHistory` entry — this adds a small amount of implementation care (keeping the two in sync) that a single-source-of-truth `status` column wouldn't require.
- **Trade-off:** A relational schema is less flexible if requirements change to need highly variable, per-department custom fields on a request — that would be more natural in a document model. We accepted this because our departments/categories are a fixed, known set for v1.
